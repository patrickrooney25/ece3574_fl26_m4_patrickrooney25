# M4 Design Note

Due Wed Oct 28, 11:59 pm. See specification Section 7.


1. Components and Threads

To keep the application responsive and prevent the window from freezing during heavy rebuilds, I will split the work across two threads. These threads will be a main GUI thread and a transient worker thread. All visual widgets (WorkspaceWidget, SearchWidget, TermInspectorWidget, ContextWidget, and SearchResultModel) will live on the GUI thread. Each widget will be created, updated, and interacted with only on this main thread. MainWindow also runs on the GUI thread with Workspace workspace_, std::unique_ptr<ProcessingCor> active_core_, and an atomic generation number called current_generation_. Whenever the user starts a build, MainWindow will start a temporary background thread using std::thread. This worker thread will run a standalone function that instantiates its own lcoal ProccessingCore, calls rebuild() againts a copy of workspace, and apply an artificial delay. The worker thread will never touch the GUI elements or shared memory to provide thread safety.

2. Corpus States and Events

The application will track the status of the corpus accross four states (NOT_BUILT, BUILDING, CURRENT, and ERROR). The program will begin in NOT_BUILT. NOT_BUILT will also be restored as the corpus state whenever the user clicks "Reset" or changes documents. In this state, corpus_current_ is fals and search, term inspection, and context actions are disabled. Once the user clicks "Build Corpus", MainWindow will increment the generation counter, take a snapshot of the workspace, spawn a worker thread, and move to the BUILDING state. While in BUILDING, the interface will be responsive and allow the user to type, edd more documents, or exit. When the worker thread finishes, MainWindow will compare the results generation tag against the active generation counter. If the tag and counter match, the state will transition to CURRENT, active_core_ will be updated, chunk counts will be displayed, and the downstream actions will be enabled. If the rebuild fails, the application will transition ot ERROR, putting the error on the status display while still keeping the workspace usable.

3. R1 and R4 Threats and Design Handling

A few user event sequences of user actions could threaten requirements. The first threat affects R2 /correctness. This is where the user starts a new build with one set of documents and while the worker thread is still running they add another file or click reset. If the worker thread finishes later and the results are accepts, the UI would have a stale index that doesn't match the current workspace. MainWindow will use a generation counter to prevent this. Any document edit or reset will increment this coutner and mark corpus_current_ as false. When a worker completes, MainWindow will only accept a new corer if its generation matches the active counter and will discard stale builds. R4 / Lifecycle is also threatened if a user clicks exit while a slow build is in progress. MainWindow will keep an std::thread handle and call join() on its exit path. This will prevent detatched threads that could cause hanging, leaking, or crashing threads. R3/Failure delivery is threatened if an unreadable document causes rebuild() to fail. The worker will catch this error and send a failure notification back to the GUI thread so the application stays usable. This will prevent the thread from dying quietly and leaving the UI stuck in BUILDING. R1/responsiveness is protected across all of these scenarios by keeping the entire build off the main thread. This allows the user to continue interacting with the GUI without it freezing.

One user scenario that could threaten R2 is if the user has one document loaded at generation 1 and clicks "Build Corpus". MainWindow would pass a copy of the workspace to a worker thread with generation 1 and set the UI state to BUILDING. While the worker processes with artificial delay, the user calls add_document_file("doc2.txt"). MainWindow would insert the file, increment the generation count, and mark corpus_current_ as false. When the worker finishes indexing document 1, it notifies the GUI thread using QMetaObject::invokeMethod. Mainwindow will compare the results from generation 1 with its current generation 2. Since the results would not match, it discards the finished core and keeps the corpus not current and presserves the central invariant.

Another scenario threatens R4  if a delayed build is actively running in the background when the user clicks "Exit". After the user confirms "Yes" on the prompt, the MainWindow will check its std::thread member. MainWindow then calls join() and waits for the worker loop to finish before destroying window resources. The application will then exit smoothly without any thread leaks or memory corruption.

4. Ownership Path of Built Corpus

The lifecycle of a built corpus follows a single owner path that moves across threads. Inside the worker thread function, a new ProvessingCore will be allocated on the heap by using std::make_unique<ProcessingCore>(), giving the worker exclusive ownership. The worker will execute rebuild() using its snapshot copy of the workspace and applies a delay. Once that is done, the worker will package the std::unique_ptr<ProcessingCore> into a result structure and send it to the GUI thread by calling QMetaObject::invokeMethod(). This moves ownership of the heap ppointer through Qts event queue. when the event executes on the GUI thread, MainWindow will take ownership of the pointer and check the generation id. If it is valid, MainWindow will move the pointer to its member variable active_core_=std::move(result.core). This will destroy the previous core. If the generation is stale or the build fails, the pointer will fall out of scope and safely deallocate the memory on the GUI thread. When the user clicks "Reset" or closes the window, active_core_.reset() will delete the core cleanly.

5. Alternative Rejected

During my initial planning I considered using a recurring QTimer on the GUI thread to periodically poll a shared std::atomic<bool>. This approach could work but it is not as architecturally sound as the event driven notification using QMetaObject::invokeMethod with Qt::QueuedConnection. Regular polling gives a bad trade off between UI responsiveness and unnecessary CPU usage. Setting the timer too short would waste CPU cycles by repeatedbly checking an incomplete task and setting it too long would give a noticeable delay between the worker thread completing and the GUI updating the corpus status and buttons. Managing a timer would also add unnecessary widget lifecycle states that must be explicitly started, stopped, and cleand up on "Reset" or "Exit". Having the worker thread post a completion event directly into Qts event loop gives an instant notification right when the build finishes instead.
